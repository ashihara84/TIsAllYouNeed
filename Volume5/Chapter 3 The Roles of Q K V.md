# 第3章　Q / K / V という役割分担

**この章でわかること**

- Query・Key・Value の、図書館のたとえ
- なぜ役割を3つに分けるのか
- embedding から線形変換で Q / K / V を作る（第2巻6章の回収）
- Q / K / V を実装して、shape を確かめる

### 3.1　Query・Key・Value のたとえ

前章では、スコア（相性）が与えられたものとして、重み付き和を作りました。

では、その相性スコアは、どうやって決めるのでしょうか。

ここで **Q / K / V** という役割分担が、登場します。

図書館の検索に、たとえると分かりやすいです。

あなたが図書館で、本を探しているとしましょう。

```text
Query（クエリ、問い合わせ）: 「私はこういう情報が欲しい」という検索キーワード
Key（キー、見出し）        : 各資料の「見出し・索引」。検索キーワードと照合される
Value（バリュー、中身）     : 各資料の「実際の中身」。取り出されて使われる
```

検索の流れは、こうです。

あなたは、自分の Query（探したいキーワード）を持っています。

それを、各資料の Key（見出し）と、照合します。

よく合う資料の、Value（中身）を、取り出します。

Attention も、これとまったく同じです。

あるトークンの Query を、全トークンの Key と照合して、相性スコアを作る。

そのスコアに応じて、全トークンの Value を、重み付き和で取り出す。

```text
相性スコア = Query と Key の照合
出力       = スコアに応じた Value の重み付き和
```

前章の「スコア → 重み → 重み付き和」の、「スコア」を作るのが Query と Key、「混ぜられる中身」が Value、というわけです。

### 3.2　なぜ役割を3つに分けるのか

「相性を測るのも、混ぜられる中身も、同じトークンのベクトルでいいのでは？」

そう思うかもしれません。

実際、すべて同じベクトルを使うことも、できます。

しかし、役割を分けると、表現力が上がります。

なぜか、考えてみましょう。

**Key と Query を分ける利点。**

「見出しとしての顔」と「問い合わせとしての顔」を、別々に学べます。

あるトークンが「探される側」のときと、「探す側」のときで、違う特徴を使えるのです。

たとえば、「本」というトークンは、「面白かった」から探されるときの顔（Key）と、自分が何かを探すときの顔（Query）を、別々に持てます。

**Value を分ける利点。**

「相性の判断に使う特徴」と「実際に運ぶ中身」を、別にできます。

相性は、ある軸で測りつつ、運ぶ情報は、また別の軸。

そういう柔軟さが、生まれます。

そこで、各トークンの embedding ベクトル `x` から、3つの異なる線形変換で、Q・K・V を作ります。

```text
Q = x W_Q
K = x W_K
V = x W_V
```

`W_Q, W_K, W_V` は、それぞれ独立に学習される、重み行列です。

第2巻6章で「embedding から Q/K/V を作る」、第3巻で「線形変換 `Wx`」を学びました。

それが、ここでそのまま効きます。

同じ `x` から、3つの違う「顔」を取り出す、というイメージです。

### 3.3　embedding から Q / K / V を作る（第2巻6章の回収）

3つの線形変換は、第3巻で使った `nn.Linear` そのものです。

入力 `x`（shape `[L, d_model]`）に、3つの `nn.Linear` を通すだけです。

```python
import torch
import torch.nn as nn

d_model = 8     # 入力の次元
d_k = 8         # Q/K/V の次元（ここでは同じにする）

W_q = nn.Linear(d_model, d_k, bias=False)
W_k = nn.Linear(d_model, d_k, bias=False)
W_v = nn.Linear(d_model, d_k, bias=False)

# 3トークンの embedding（第4巻の出力にあたる）
x = torch.randn(3, d_model)   # [L=3, d_model=8]

Q = W_q(x)   # [3, d_k]
K = W_k(x)   # [3, d_k]
V = W_v(x)   # [3, d_k]

print(Q.shape, K.shape, V.shape)   # すべて torch.Size([3, 8])
```

入力の同じ `x` から、3つの異なる重みで、3つの異なるベクトル Q・K・V が、作られます。

同じトークンでも、

- 「問い合わせとしての顔（Q）」、
- 「見出しとしての顔（K）」、
- 「中身（V）」、

が、別々に得られるわけです。

`bias=False` にしているのは、Attention の Q/K/V 射影では、慣習的にバイアスを使わないことが多いからです（必須ではありません）。

### 3.4　Q / K / V を実装して shape を確かめる

shape の流れを、改めて追っておきましょう。

これは、次章以降で、ずっと効きます。

```text
x : [L, d_model]      … L トークン、各 d_model 次元
Q : [L, d_k]          … 各トークンの Query
K : [L, d_k]          … 各トークンの Key
V : [L, d_k]          … 各トークンの Value
```

入力 `x` が `[L, d_model]`、Q・K・V が `[L, d_k]`。

線形変換で、次元が `d_model` から `d_k` に変わっています（ここでは同じ8にしましたが、変えることもできます）。

バッチ付きなら、先頭に `batch` がつくだけです。

```python
import torch
import torch.nn as nn

d_model, d_k = 8, 8
W_q = nn.Linear(d_model, d_k, bias=False)
x = torch.randn(2, 3, d_model)   # [batch=2, L=3, d_model=8]
Q = W_q(x)
print(Q.shape)                   # torch.Size([2, 3, 8])  [batch, L, d_k]
```

`[2, 3, 8]`（batch, L, d_k）です。

第3巻で学んだとおり、`nn.Linear` は最後の次元にだけ作用し、先頭の `[batch, L]` はそのまま保たれます。

これで、相性スコアを作るための材料（Q と K）と、混ぜられる中身（V）が、別々に手に入りました。

次章で、この Q と K の内積から相性スコアを作り、softmax で重みにして、V を重み付き和にします。

第2章の核（スコア → 重み → 重み付き和）と、この章の役割分担（Q/K/V）が、ついに合流します。

### 3.5　本章のまとめ

- Q（問い合わせ）・K（見出し）・V（中身）の役割分担。図書館の検索のように、Query を Key と照合し、Value を取り出す。
- 役割を分けると、「探す顔／探される顔／運ぶ中身」を別々に学べて、表現力が上がる。
- Q/K/V は embedding `x` に、3つの独立な線形変換 `W_Q, W_K, W_V` を通して作る（第2巻6章・第3巻の回収）。
- shape は `x:[L,d_model]` → `Q,K,V:[L,d_k]`（バッチ付きで先頭に batch）。
- 第2章の「核」と、この章の「役割分担」が、次章で合流する。
